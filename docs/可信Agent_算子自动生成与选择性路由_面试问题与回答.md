## 如何使用

- **第一遍：**读“一页事实卡”、Q01、Q02、Q21、Q51、Q65—Q80、Q91—Q106，以及最后的三段口述稿。
- **第二遍：**按“问题 → 回答 → 面试官继续追问”的顺序练习，每题先用 30—60 秒回答。
- **第三遍：**准备一个完整专项算子案例、一个非专项回归案例、一个评分器误判案例，能打开对应代码和日志说明。
- **标记：**`P0` 必须熟练；`P1` 常见深入问题；`P2` 扩展问题。未标已完成的改进方案都只能作为设计回答，不能说成已落地。
- **版本原则：**历史双算子实验、后续生成算子实验、FlowEvo 预算与评测实验是不同协议，数字不能互相补证。

## 第一部分：项目介绍、动机与个人贡献（Q01—Q10）

### Q01｜P0：用一分钟介绍这个项目。

**推荐回答：**我研究的是 Agent 遇到可复现的长尾失败以后，能否把解决办法沉淀成可复用算子，并且只在适用时调用。流程是先审计失败、归纳能力需求，再生成候选，通过静态检查、受限执行、隐藏集和回归验证，最后根据输入特征和历史证据选择算子，不满足条件就回退通用流程。双算子构造混合隐藏实验中，48 道题各跑 3 次，限时严格正确数从 96/144 提升到 132/144。我也做了 FlowEvo 的提取与评分对照，防止把截断或评分错误误判成能力缺口。当前结果主要支持有限机制内的复用与协同，自动化和自然分布覆盖仍有边界。[S1][S2][S7]

### Q02｜P0：你的核心创新点是什么？

**回答要点：**重点是把“生成一个工具”扩展成“以失败证据驱动、经过独立验证、带适用边界和版本证据的能力管理闭环”。可分为三个贡献：从稳定失败形成结构化需求；把候选和可上线算子分离；让路由同时受适用性、禁止边界与历史净收益约束。不要声称提出了新的区间 DP 或素数算法，也不要在没有系统文献比较时宣称首次提出。

### Q03｜P0：为什么要自动生成算子，已有工具调用不够吗？

**回答要点：**已有工具调用通常假设能力库已经存在。本项目关注库中缺少某种稳定能力时，如何从失败中形成候选，再决定是否值得加入。收益是跨实例复用，代价是离线构建和验证成本。只有任务重复出现且可验证时，沉淀算子才可能划算。

### Q04｜P0：这里的“算子”到底是什么？

**回答要点：**是一个有统一输入输出接口、明确适用范围、失败边界、资源约束和版本的执行单元。它可以封装提示工作流，也可以封装确定性程序。两个专项案例最终采用确定性精确计算，但“算子”这个抽象不等于所有算子都必须是纯算法函数。

### Q05｜P0：它和临时写一段 Python 有什么区别？

**回答要点：**临时代码主要解决当前实例；入库算子要能参数化处理一类问题，接受跨实例验证，明确何时拒绝，并绑定代码版本和验证证据。两者都可以由模型生成，关键区别是能力是否被沉淀、验证和受控复用。

### Q06｜P1：为什么选择 AFlow？与它的关系是什么？

**回答要点：**AFlow 提供工作流、模型调用和基础算子等可复用基础，我在其上扩展能力生成、验证和证据路由。需要区分复用原框架与自己新增的模块。历史主对照具体是通用两阶段求解流程，不能随意称为“在相同搜索预算下战胜 AFlow 最优工作流”。[S4][S5]

### Q07｜P1：AFlow 与 FlowEvo 在项目中分别承担什么角色？

**回答要点：**AFlow 线主要用于算子库、候选验证和路由闭环；FlowEvo 线用于扩展基准执行、响应提取、数学等价判定和成本审计。两条线共同服务“真实识别能力缺口”，但有不同的数据、基线和协议，不能合并成一个实验。

### Q08｜P0：哪些工作是你做的？哪些来自开源框架或 AI 辅助？

**回答方式：**按“原框架能力 → 我新增或修改的模块 → 我负责的设计和验证 → 使用的辅助工具”展开。可拿出候选验证、路由证据、响应提取、类型评分和实验账本对应文件。简历写独立开展的实验可说明自己负责，但个人逐行编码比例、导师参与和 AI 参与不能从仓库推断，面试前按真实情况补全。不要把复用模块和辅助生成代码全部说成手写。

### Q09｜P1：最难的问题是什么？

**推荐回答：**最难的是判断一次未通过到底是什么失败：模型解错、程序执行异常、预算截断，还是提取和评分器误判。归因错了，后面会为不存在的能力缺口生成算子。我通过保留原始响应、结束原因、API 用量和评分过程，将这些问题分开，再用冻结对照检查改进来源。

### Q10｜P1：为什么称“可信”，是不是已经保证正确？

**回答要点：**可信指行为和证据可审计、适用范围可约束、失败可拒绝、结果有独立评测，并非对所有输入保证正确。代码哈希保证版本绑定，测试提供经验性证据，算法证明提供域内逻辑依据，三者作用不同。

## 第二部分：失败发现与机制归纳（Q11—Q20）

### Q11｜P0：什么是“稳定失败机制”？怎么判定？

**回答要点：**历史原型先排除坏题、评分误判和执行异常；同题独立运行 3 次，至少 2 次真实求解失败，才标记稳定失败题；机制层面要求至少 3 道不同稳定失败题，并使用审计错误率不低于 0.20 的操作门槛。这是特定协议下的筛选规则，不是跨模型、跨提示的数学定理。[S8]

### Q12｜P1：为什么重复 3 次、2 次失败？统计上充分吗？

**回答要点：**这是成本与筛查灵敏度的折中，只能降低单次波动影响，不能给出很强统计保证。应结合跨题一致性，并在后续增加重复数、置信区间和阈值敏感性分析。不能从 2/3 失败推断模型真实错误率必然超过某个值。

### Q13｜P1：0.20 阈值怎么来的？有没有调参？

**回答要点：**历史口径把它作为预先设定的操作阈值，避免很低频错误也触发构建成本。不能说理论最优；需要在独立开发集比较 0.15、0.20、0.30 等设置的候选质量、覆盖和成本。当前不把 Wilson 或 Clopper–Pearson 置信下界说成已实现的硬门槛。[S8]

### Q14｜P0：怎么排除 Prompt、温度和偶然采样导致的失败？

**回答要点：**固定模型配置与协议、进行同题重复和跨题验证，可以提供可复现证据；系统性的 Prompt 扰动、温度分层和跨模型实验才更能区分配置缺陷与能力缺口。历史材料没有完成这些全面检验，因此应说“当前工作流下稳定失败”，不能说模型本体必然不会。

### Q15｜P1：怎么把多个失败归为同一个机制？

**回答要点：**以相同被违反的约束、可定位的错误步骤和可观察适用条件分组，不能仅按“都是数论”或关键词聚类。后续机制归纳实现要求引用具体失败运行的原始片段 ID，输出适用范围、反例和不确定性；这些输出先作为假设，不自动获得生成或晋级权限。不要把后续实现倒写成历史 v2 工具的全部生成过程。[S9]

### Q16｜P1：LLM 归因也可能幻觉，怎么约束？

**回答要点：**让归因引用可回查的片段、偏移和运行 ID；原文由程序取回，避免模型编造错误引文；允许输出评分歧义或 Unknown。引用真实只能证明证据存在，不能自动证明解释正确，还需要规则校验、复核和独立实例验证。

### Q17｜P1：只有失败样本，能算错误率吗？

**回答要点：**不能。失败样本可以诊断错误类型，却缺少总体分母。机制错误率必须从对应机制的完整有效运行中统计，保留成功样本、异常样本和排除理由。机制归纳脚本也明确将输入标为 failure-only，禁止从中报告总体错误率。[S9]

### Q18｜P1：怎么避免把超时当成数学能力不足？

**回答要点：**区分模型持续生成耗尽预算、工具算法复杂度过高、API 连接超时和控制器未完成提交。限时成功指标里超时算未成功，但机制归因中必须分开。专项算子减少超时是交付可靠性收益，不自动等价于基础模型学会了数学。

### Q19｜P1：机制有重叠，或者一个题有多种错误怎么办？

**设计回答：**把机制作为可多标签的假设，记录最早可确认偏差、后续传播和不确定性；适用边界依据输入条件表达。若无法区分，就暂不据此生成可上线算子，优先补反例或人工复核。不要强行让每个失败都归入已有机制。

### Q20｜P2：模型升级后，原来的稳定失败还存在吗？

**设计回答：**未必。需要把基线模型配置、提示与证据版本绑定，重新评估专项收益和维护价值。新模型已经解决的问题，可以减少路由或退役算子；不能无限继承旧模型下的胜负证据。

## 第三部分：需求规格与算子生成（Q21—Q30）

### Q21｜P0：你说自动生成，到底哪些自动，哪些人工？

**推荐回答：**当前应称为半自动闭环。人工参与错误审计、机制边界、题族与元规则设计；系统执行轨迹采集、统计、规格填写、候选生成和预设门槛评测。历史两个高可信 v2 工具包含确定性材料化与审查，不能说是从任意日志完全自主发明算法。后续单独的生成算子实验保存了真实候选源码与生成权限，可以证明该实验的生成过程，但不能替历史工具补写来源。[S8][S10]

### Q22｜P0：结构化规格里有哪些字段？为什么不用自然语言？

**回答要点：**至少描述目标能力、输入输出契约、参数域、适用特征、禁止条件、资源上限、验证性质和失败回退。自然语言负责表达意图，结构化字段支持自动校验、版本比较、执行约束和测试生成。具体字段以对应版本 schema 为准，不把设计字段说成所有版本都已保存。

### Q23｜P1：生成器可以看到哪些内容？

**回答要点：**应当能看到 Design/Discovery 集、对应失败轨迹、结构化需求、工具接口和开发反馈；不能看到当前版本的隐藏评测题、答案、失败轨迹或参考求解器源码。历史生成权限需检查实际请求记录；后续 Experiment A 明确只提供公共规格、30 道独立小规模训练样例及答案、环境和候选验证反馈。[S10]

### Q24｜P1：如果生成器看过参考答案，不就作弊了吗？

**回答要点：**开发样例带答案是合法监督，关键在于数据角色和隔离。隐藏题答案只能用于评分，不能用于候选修复或筛选。如果看过隐藏内容再修改候选，这批数据就成为开发证据，新版本必须换独立隐藏集。

### Q25｜P1：生成一次失败了怎么办？能修复多少次？

**回答要点：**在开发阶段按预先设定的候选数、修复次数和总预算修复，记录所有尝试；隐藏评测后的失败不能继续在原隐藏集上刷过关。不同版本预算不同，例如后续 Experiment A 设最多 3 个候选、各 3 次修复、首个准入即停止，不能套到历史双算子实验。[S10]

### Q26｜P1：怎么避免生成器只记住几个样例？

**回答要点：**检查参数化接口、源码中是否硬编码答案、独立参数实例、表述变体、边界和近似反例；有条件时采用规模外推或约束组合外推。字符串去重不够，仍需防模板同构泄漏。测试通过也不等于证明没有过拟合。

### Q27｜P1：模板生成是不是根本没有新能力？

**回答要点：**要拆开算法先验、候选组合与运行能力。如果算法已经人工写入模板，不能把收益包装成自主算法发现；但把能力变成参数化、可验证、可拒绝的执行单元仍有工程价值。研究自动生成能力时，应单独设置自由代码、受约束模板和人工工具对照。

### Q28｜P1：为什么不直接让 LLM 每题调用 Programmer？

**回答要点：**可以作为强基线。临时程序生成每次都要支付规划、写码和调试成本，且可能重复犯错；冻结算子可以摊销这些成本。不过如果基线没有同等 Python 权限，就无法分清收益来自“能执行代码”还是“可复用算子”，因此公平实验必须控制工具权限。

### Q29｜P1：生成的只是 Prompt，能叫算子吗？

**回答要点：**只要具有统一接口、边界和可复用行为，可以是提示型算子。但提示型与确定性程序型算子的验证强度不同，应分别统计。如果只是把题目答案换成一段提示而没有跨实例证据，不能说明形成了稳定能力。

### Q30｜P2：什么时候不应该生成新算子？

**回答要点：**一次性问题、低频机制、无法可靠验证、输入域不明确、构建维护成本超过预期收益，或更强通用模型已经廉价解决时。可以先修 Prompt、提取器、资源配置或接口，避免把基础设施故障都转成新算子。

## 第四部分：验证、安全与生命周期（Q31—Q40）

### Q31｜P0：一个候选从生成到入库要经过哪些关卡？

**回答要点：**静态与接口检查 → 受限环境冒烟 → 开发集功能验证 → 边界与反例验证 → 冻结候选 → 隐藏集确认 → 非专项回归 → 满足预先条件后准入。具体版本可能有差异，不能把“跑通一个样例”直接等同于生产可路由。

### Q32｜P1：静态检查具体检查什么？

**回答要点：**语法、接口、允许导入、危险名字与属性、禁止动态执行和文件网络进程访问等。当前生成数学程序 guard 使用 AST 遍历、导入白名单和受限 builtins。它是有限语言的防护层，源码明确说明不是通用安全边界。[S11]

### Q33｜P0：AST 白名单能保证沙箱安全吗？

**推荐回答：**不能。它能阻止显式危险语法，但不能完整覆盖语言运行时漏洞，也不能限制所有资源消耗。生产环境需要进程或容器隔离、最小权限、禁网、文件系统隔离、CPU/内存/时间限制和可终止 worker。项目中“做了静态检查”和“具备强安全隔离”必须分别说明，不能把前者当成后者的证明。

### Q34｜P1：测试都通过，为什么还可能不正确？

**回答要点：**有限测试可能漏边界，生成器与参考可能共享 bug，解析器可能误解题意，域外输入也可能触发。应结合小规模独立暴力 oracle、算法推导、性质测试、差分验证和保守拒绝。测试支持经验可靠性，不能直接冒充全域形式化证明。

### Q35｜P1：怎么构造边界测试和近似反例？

**回答要点：**边界测试验证合法域的极端参数，如最小规模、零、重复值和资源上限；近似反例验证语义相邻却不该调用的题，如“括号化方法数”而非“不同结果数”、允许重复数字而非无重复、求概率而非计数。两类测试目的不同。

### Q36｜P1：验证器本身错了怎么办？

**回答要点：**保存原始预测、标准答案、提取结果、类型与判定依据；对冲突进行独立复核。评分器修复后用同一冻结评分器重评两组，保留旧分数与版本。若评测题参与了修复，之后的成绩应标注事后开发影响，需要新测试集确认。

### Q37｜P1：为什么需要版本号和哈希？

**回答要点：**避免“测试的是 A，上线的是 B”。版本帮助表达演进，哈希校验源码、提示、运行依赖和数据是否一致；历史证据只对相应修订有效。哈希本身不证明代码正确、安全或时间真实，只证明内容一致性。[S3][S4]

### Q38｜P1：修改一行 Prompt 或依赖后，原证据还能用吗？

**回答要点：**行为相关改动需要重新绑定修订，旧证据可留作历史，但不能直接用于新版本准入。当前库支持修订变化后清空当前有效证据，路由加载也校验类、提示及部分运行依赖哈希。[S3][S4]

### Q39｜P1：算子上线后变差了，怎么回滚？

**回答要点：**保留旧版本与证据、禁止问题版本继续被路由，恢复经过验证的版本或通用回退。当前库具备生命周期状态与证据门槛；滚动窗口自动降级、漂移监控和完整自动淘汰策略不能说成全部已实现。生产方案需另做验证。

### Q40｜P2：能做形式化验证吗？

**回答要点：**对有限精确算法，可以证明递推或枚举的域内正确性，再验证实现与规格一致；但自然语言解析、运行环境和输出解释仍是独立风险。优先选择小而清楚的核心函数做证明或穷举验证，不把整个 Agent 系统轻易宣称为形式化可信。

## 第五部分：两个专项算子的算法细节（Q41—Q50）

### Q41｜P0：括号化去重算子解决什么，为什么模型容易错？

**回答要点：**给定数和运算符的顺序，考虑所有完整括号化，统计能得到的不同数值。容易把括号化结构数量当结果数量，或枚举遗漏、重复计数。应先明确是不同数值，不是括号方案数，也不是允许重排数字。[S6]

### Q42｜P0：区间 DP 的状态和转移怎么写？

**回答要点：**令 `V[i][j]` 是区间 i 到 j 可产生的全部结果集合；单个数的集合只含自身。枚举根处分割点 k，把左集合和右集合按原位置运算符做笛卡尔积运算，加入当前集合。最后返回 `len(V[0][n-1])`。集合完成去重，转移同时覆盖所有合法二叉表达式树。

```text
V[i][i] = {a[i]}
for length in 2..n:
    for each interval [i,j] of this length:
        for k in i..j-1:
            for x in V[i][k]:
                for y in V[k+1][j]:
                    V[i][j].add(apply(op[k], x, y))
```

### Q43｜P1：证明这个 DP 正确。

**回答要点：**按区间长度归纳。长度 1 显然正确；任何更长合法括号表达式都有一个根分割 k，左右子表达式的值由归纳假设覆盖，因此不会遗漏。反过来，每次转移都由合法左右表达式按原运算符组合，所以不会产生非法值。集合只去掉数值重复，不丢失可达值。

### Q44｜P0：复杂度是不是 O(n³)？

**回答要点：**不能只说 O(n³)。区间和分割约 O(n³)，但每个分割还需要左右结果集合的笛卡尔积。更准确是对所有 `(i,k,j)` 求和 `|V[i][k]| × |V[k+1][j]|`，再考虑大整数运算成本；若集合大小上界为 S，可粗写 O(n³S²)，空间 O(n²S)。集合可能迅速增长。[S6]

### Q45｜P1：支持什么输入？为什么要限制规模？

**回答要点：**当前实现使用非负整数操作数以及 `+、-、*`，中间结果可以为负；最多 13 个操作数，每个区间结果集合上限 500,000。除法、负数词法、重排或超限输入不能假装支持。还需要注意大整数位长与同步 CPU 执行的资源风险。[S6]

### Q46｜P1：给一个最小的“方案数不等于结果数”的例子。

**回答要点：**`1+2+3` 有两种完整括号化，结果都是 6，因此不同数值数是 1。`1+2*3` 则可得到 7 和 9，不同数值数是 2。前者直接检查是否误用了 Catalan 数作为答案。

### Q47｜P0：受限数字素数算子怎么工作？

**回答要点：**解析数字集合、允许长度范围和无重复约束，枚举各长度的排列，排除前导零，转为整数，做确定性试除判素，最终统计素数集合大小。这里解决的是受限集合内的有限枚举计数，不是任意规模的素数生成问题。[S6]

### Q48｜P1：为什么 1 不是素数？前导零、重复数字怎么处理？

**回答要点：**小于 2 判非素数，2 和 3 特判；数字集合必须没有重复元素；排列本身不重复使用元素；首位为零的排列排除。包含 0 时，检测器要求题面明确涉及前导零的约束，避免擅自解释题意。解析失败或长度不合法要拒绝。[S6]

### Q49｜P1：枚举素数的复杂度和上限是什么？

**回答要点：**候选数量为 `P = Σ d!/(d-l)!`，每个候选最坏试除到平方根，粗略为 O(P√M)，还忽略了大整数成本。当前最多 10 个不同数字，枚举上限 1,000,000；上限限制了候选量，但不等于严格的时间保证。可以优化末位、数位和、缓存或判素算法，但不能说这些都已实现。[S6]

### Q50｜P1：这两个算法这么普通，研究意义在哪里？

**回答要点：**普通算法作为案例有利于验证正确性和分析失败。研究问题是如何从失败形成可复用能力、控制准入并选择性调用，不是声称发明 DP 或判素算法。但只有两个窄机制确实不足以证明通用性，需要更多机制、自然分布和同权限强基线。

## 第六部分：选择性路由、拒绝与回退（Q51—Q64）

### Q51｜P0：路由器具体怎么选算子？

**推荐回答：**当前路由不调用 LLM，而是从题目抽取可观察特征，先检查硬失败边界，再匹配适用规则，读取与当前算子版本和规则范围对应的历史配对证据，计算分数并检查最低证据门槛。满足阈值才执行；没有安全候选就走通用两阶段流程。这里的“高置信”是规则和证据达到门槛，不是模型输出了一个校准概率。[S3][S4]

### Q52｜P0：分数怎么算？0.70 意味着 70% 正确率吗？

**回答要点：**当前代码的启发式分数是 `clip(w_rule + 0.15×net + 0.05×volume, 0, 1)`，其中 `net=(wins-losses)/(wins+losses+2)`，`volume=min(1, observations/20)`。另有证据硬门槛。0.70 是最低选择分数，不代表 70% 正确率，也不是理论最优阈值。[S3]

### Q53｜P1：既然有分数，为什么还要硬门槛？

**回答要点：**避免规则权重大却缺乏证据的候选直接上线。当前默认至少 6 条观测、净胜至少 2、至少 2 道不同题、至少 2 道不同获胜题，记录可配置这些条件。不同问题数约束能降低同一题重复运行刷高证据量的风险，但不能完全解决相关性。[S3]

### Q54｜P1：是不是关键词匹配？表述换一下还行吗？

**回答要点：**当前有规则、正则和参数解析，因此语言覆盖确实有限，不应包装成通用语义理解。需要表述改写、否定句、歧义、多表达式、语言变换等独立测试。当前隐藏集做过冻结特征过滤，零误路由不能证明面对任意自然表述都可靠。

### Q55｜P1：为什么不让 LLM 来路由？

**回答要点：**少量机制下，确定性规则成本低、可复现、容易审计；LLM 路由可能扩大语言覆盖，但有额外调用成本和不确定性。更大库可以考虑模型召回加确定性边界校验，但需要对照准确率、覆盖率、误触发和成本，不能只凭直觉说更好。

### Q56｜P0：两个算子都匹配怎么办？

**回答要点：**当前会对符合条件的候选做证据与分数排序，取满足条件的候选。分数接近时应怎样拒绝或消歧，是进一步完善方向；不能把冲突裕量和不确定性校准说成已完成。双算子实验没有观察到交叉路由，不代表实现已经解决大规模冲突。

### Q57｜P1：怎样避免“宽泛强算子”抢走所有题？

**回答要点：**适用规则必须有可检验输入条件，禁止条件和硬边界优先；历史证据按适用范围统计，避免用一个领域的胜绩支持所有领域。还应专测边界重叠和相邻机制。把工具描述写得越宽越好，会增加误触发风险。

### Q58｜P0：执行前拒绝与执行后回退有什么区别？

**回答要点：**执行前拒绝发生在没有匹配规则、证据不足或命中禁止边界时；执行后回退发生在参数解析失败、工具拒绝、异常或没有有效响应时。两者都要记录原因。回退能恢复通用能力，但前面已消耗的时间和资源不会自动退还。

### Q59｜P0：算子输出错误答案但状态是 success，会自动回退吗？

**回答要点：**不一定。当前路由对执行状态和有效响应做检查，无法在没有 oracle 的情况下发现所有语义错误。只有额外的独立验证器发现问题才可能回退。因此入库前验证很重要，不能说系统知道答案错了就总能自愈。

### Q60｜P1：180 秒是每个阶段各 180 秒吗？

**回答要点：**不是。历史评测用外层 `asyncio.wait_for` 包住一次完整求解，路由、算子执行与可能的回退共享 180 秒总墙钟。回退得到的是剩余时间，不能说最多多次 180 秒。同步 CPU 是否能被及时打断还涉及进程隔离问题，见 Q112。[S5]

### Q61｜P1：回退是不是保证不会比基线差？

**回答要点：**不保证。算子尝试可能占用预算，错误 success 也可能绕过回退；即使直接进入同一通用流程，重新采样也会不同。实际非专项从 87/96 下降到 84/96，就是必须保留的系统表现。

### Q62｜P1：如果把阈值调高，准确率是不是总能提高？

**回答要点：**专项覆盖率会下降，回退成功率和误触发成本共同决定总体效果，未必单调。应该在独立开发集画风险—覆盖曲线，报告阈值变化对专项调用率、错误率、总成功率和成本的影响，不能只看被调用样本准确率。

### Q63｜P1：算子库扩大到 100 个怎么办？

**设计回答：**按任务域、输入类型和能力分层召回，再做硬约束与证据排序；缓存特征，处理同义规则，加入冲突集和版本索引。检索可从线性扫描转为结构化索引或向量召回，但仍需验证语义边界。当前双算子结果不足以支持百算子扩展性结论。

### Q64｜P2：为什么不直接训练一个分类器或 MoE？

**回答要点：**可以作为替代路线，但需要足够的路由标签、负例、漂移处理与校准。当前小库采用可审计规则更容易控制边界；算子是外部可执行能力，和参数化专家的训练机制不同。应比较数据成本和实际风险，不把名称相似当技术等价。

## 第七部分：144 条隐藏观测的完整审问（Q65—Q80）

### Q65｜P0：144 条数据究竟怎么来的？

**推荐回答：**48 道题组成构造混合集，每题两组各运行 3 次，因此每组 144 条观测。48 题由 8 道括号化正例、8 道素数枚举正例、24 道普通 MATH 题、两类各 4 道近似反例组成。专项题按固定种子参数化生成并变换表述，普通题从已有 MATH 测试文件抽取，混合后打乱；检查与历史题目的稳定 ID 不重合。它验证已知机制内跨实例复用与协同，不是随机自然题分布。[S1][S2]

### Q66｜P0：何时封存，怎么证明不是结果出来后改的？

**推荐回答：**记录显示 2026-08-20 08:25:55 UTC 先保存准备协议，冻结两个 v2 算子的哈希、数量配比、执行配置和门槛；随后生成数据并保存数据哈希。09:04:11 UTC，在正式加载评测题前保存运行协议，绑定数据、路由、评分器和依赖哈希。完成后记录结果哈希，禁止在原种子调参重跑。它提供仓库内可追溯性，但不等于公开注册或第三方时间戳证明。[S1]

### Q67｜P0：你这个隐藏集有没有按现有工具筛题？

**推荐回答：**有适用性校验，需要主动说明。构造后，正例必须被冻结特征识别，并由冻结工具求解且通过评分；普通题与近似反例不能触发专项特征。代码在检查失败时中止构建，不应把它描述成完全独立于方法的随机抽样。即使不是不断重抽到通过，也已经限制了测试支持范围，所以 48/48 和零误路由主要是受约束协同确认。[S2]

### Q68｜P0：那这是不是循环论证，实验没有价值？

**回答要点：**它对“域内工具算法是否能解所有任意输入”的证明力弱，也不能无偏估计路由覆盖；但仍能检查系统集成、两类算子共存、限时交付、回退和逐次结果。更强实验应先独立冻结题族与自然样本，不用被测路由或被测工具决定入集，再报告命中率和净收益。承认当前实验定位，避免用一个结果回答所有问题。

### Q69｜P0：生成算子时能看到这些隐藏题吗？

**回答要点：**这批题在工具版本冻结后生成，所以从顺序上隔离了本次新实例。正式求解器只收到 `problem`，`solution` 与元数据留给评分和审计。不过开发者知道机制和生成规则，普通题来自公开基准，也不能由此证明模板未知、语义完全无重叠或预训练无污染。历史生成上下文还需单独核验。[S1][S2][S5]

### Q70｜P0：基线和改进方法是不是相同模型、相同预算？

**推荐回答：**同一个执行模型配置，协议写 deepseek-v4-flash；同一数据、同样 3 次重复、每次 180 秒总上限，共用评分器和通用回退。基线是通用两阶段求解，改进是双算子路由后必要时回退。但没有据此建立严格等 token、等 CPU、等候选生成成本的对照，因此应说“同模型配置、同总时间上限”，不能笼统说完全等预算。[S1][S5]

### Q71｜P0：模型版本和温度真能保证一致吗？

**回答要点：**代码两组从同一个配置对象创建模型，但本次冻结协议没有逐项列出温度和 token 上限。应核对历史配置快照、实际 API 请求和服务响应，不能拿现在配置补写当时参数。服务端模型别名还可能漂移，同名模型不等于不可变权重版本。

### Q72｜P0：严格正确数的“严格”是什么意思？

**回答要点：**主指标为 `correct_within_timeout`，即在总时限内完成，并由冻结版本评分器判对。不是形式化证明绝对正确，也不是只要推理中出现过正确答案就算对。需固定参考、提取和比较逻辑，异常和未完成保留在原分母。

### Q73｜P0：96→132 到底增加了多少？

**回答要点：**净增 36 条；准确率 66.7%→91.7%，增加 25 个百分点。相对正确率提高 37.5%，未成功数从 48 降到 12、减少 75%。这些是不同分母，现场优先说“增加 25 个百分点”，不要混用“提高 25%”。

### Q74｜P0：凭什么说收益来自算子，而不是随机性？

**推荐回答：**分项结果与执行轨迹提供机制性证据：括号化 9→24、素数 0→24，专项合计增加 39；非专项 87→84，减少 3，所以净增 36。所有专项都调用对应工具，没有交叉路由；超时 39→1，与确定性计算替代长推理相符。后续五种子都观察到正提升。但这支持算子加路由整体干预，不能独立识别二者各自的因果贡献。[S1][S6]

### Q75｜P0：怎么证明是路由有效，而不是工具本来就强？

**回答要点：**当前主要证据是专项命中、普通题拒绝和跨算子无冲突，证明有限范围内的协同；由于构造时有特征校验，这不能充分证明自然路由泛化。需要加入 oracle 路由、现有规则路由、LLM 路由、无边界路由等对照，以工具固定不变、只换路由来测独立贡献。

### Q76｜P0：非专项新增的 3 次错误是什么？

**回答要点：**涉及两道题：时钟概率题在两次重复中由通用回退给出错误答案；单位根求和题一次通用回退超时。三次都没有选择专项算子，因此不属于误路由，但它们仍是完整系统的真实退化，不能删去或说“完全无副作用”。[S1][S8]

### Q77｜P1：零误路由、专项 100% 召回能否说明系统可信？

**回答要点：**只能说明当前构造且筛过适用性的有限样本中没有观察到相应错误。普通题与反例共有 32 道独立题，重复 3 次不会增加输入覆盖；路由本身还是确定性的。零事件不代表真实错误率为零，更不能从中推断百算子规模可靠。

### Q78｜P1：为什么选 48 道，配比会不会放大收益？

**回答要点：**这是一种用于联合确认的构造配比，专项占 1/3，确实可能高于自然分布覆盖率。应该分别报告专项、非专项和总体，并在独立自然测试集估计实际命中比例。不能把 25 个百分点直接迁移到真实用户流量。

### Q79｜P1：跑失败了会换种子吗？这会不会选择性报告？

**回答要点：**协议禁止原种子调参刷结果，并规定正式失败需要新种子，但这条规定本身不能消除选择性报告风险。必须保存全部尝试与失败原因，区分基础设施无效运行和方法未达门槛；方法失败要计入汇总。现有“5 个正式完成且通过”的报告不能单独证明没有其他未报告尝试，需审计完整运行目录。[S1][S6]

### Q80｜P1：五随机种子结果能补充什么？

**回答要点：**汇总 720 条观测，462→673，224 次改善、13 次退化；五种子平均准确率从 64.17% 到 93.47%，说明在这些构造种子上不是单个幸运结果。总 token 从 4,177,391 到 2,885,006。但五个种子仍沿用机制与构造方法，不能补足自然分布、构造过滤和未报告尝试的风险。[S6]

## 第八部分：统计、因果归因与成本（Q81—Q90）

### Q81｜P0：144 条能当独立样本计算显著性吗？

**回答要点：**不能简单当作 144 道独立题。重复运行共享题目与路由条件，存在相关性；应以题目为配对或聚类单位，按题目汇总或做 cluster bootstrap。五种子分析也应区分数据种子变化和单题重复采样，不能无限放大样本量。

### Q82｜P1：为什么要做配对比较？

**回答要点：**同一题同一协议比较可减少题目难度差异。主种子 39 胜、3 负比只给两个准确率更清楚，但同一运行编号不代表两组共享完全相同随机噪声。若做 McNemar 或 bootstrap，也要明确统计单位及重复相关性。

### Q83｜P1：置信区间或 p 值能证明因果吗？

**回答要点：**不能。它们处理指定统计假设下的采样不确定性，不修复数据选择、预算不等、评分变化或泄漏问题。因果归因首先依赖控制变量、预先协议、消融和独立数据，然后再报告统计区间。

### Q84｜P0：最重要的消融实验有哪些？

**设计回答：**固定模型、工具权限、预算和数据，比较：通用流程；通用流程加临时 Python；仅括号化；仅素数；双算子加当前路由；双算子加 oracle 路由；双算子去掉硬边界或版本证据。报告正确率、超时、非专项退化、路由错误和成本；不是只比较一个弱基线。

### Q85｜P1：怎么区分确定性工具收益和“自动生成”收益？

**回答要点：**人工实现工具、模型生成工具、临时生成程序和无工具基线应分别对照；同一个工具再比较固定调用与选择性路由。历史工具的协同结果不能独自证明自动生成能力；后续保存真实生成轨迹的实验可以回答部分问题，但任务与协议必须另列。

### Q86｜P0：公平预算应包括什么？

**回答要点：**在线模型调用、输入/输出 token、工具 CPU/内存/墙钟、回退、失败请求、重试，以及离线生成、修复、验证和维护。可以分别报告在线等预算与生命周期总成本，不要假装一个口径覆盖所有公平性问题。

### Q87｜P1：一次性构建成本怎么摊销？

**回答要点：**设构建验证成本为 `C_build`，每次命中相对基线节省 `ΔC_hit`，粗略命中回收点为 `C_build/ΔC_hit`，前提是节省为正。若按总请求量算，还需考虑命中比例、误路由损失和所有请求的路由成本。人工维护和本地计算不能默认为零。

### Q88｜P1：为什么日志费用显示 0，能说免费吗？

**回答要点：**不能。五种子报告明确指出零费用来自价格映射未配置。应使用真实 API 用量，必要时给价格版本下的估算，并区分估算与实际账单。缺失 usage 单列，不按零处理。[S6]

### Q89｜P1：准确率提高但更贵，算成功吗？

**回答要点：**取决于业务目标。要报告准确率—成本—时延的 Pareto 关系，并在明确约束下比较。算子线的部分实验节省 token，不意味着 FlowEvo 高预算线也省；MATH 那组实际上增加 55.45%，只能讨论以更多预算换取更高完成率。

### Q90｜P1：自然分布的净收益怎么估计？

**设计回答：**先独立采样流量，估计真实命中比例 p。总体成功率变化可粗略分解为 `p×专项成功率差 + (1-p)×非专项成功率差`，再细分误路由和拒绝。它是解释性分解，实际应在自然全分母数据上直接评测，并记录覆盖率和成本。

## 第九部分：FlowEvo 扩展评测、预算与评分（Q91—Q106）

### Q91｜P0：为什么简历还写了 FlowEvo 评测？与可信算子有什么关系？

**回答要点：**可靠地发现失败，是可信能力演进的前提。原始零分可能来自模型解错，也可能来自截断、答案提取和比较器覆盖不足。我在 FlowEvo 的五基准评测中把这些因素分开，因此不会一看到低分就生成新算子。不过这条线的预算和评分收益不是双算子路由收益。[S7]

### Q92｜P0：MATH 605 题是什么？是标准测试集吗？

**回答要点：**当前实验文件中合计 605 题，包括 119 验证题和 486 测试题。可以作为工程全量对照，但主泛化成绩应单列测试部分，不能写成 605 道纯测试题或官方完整 MATH 测试集。也要与历史其他 500 题版本区分。[S7]

### Q93｜P0：461→572 是怎么得到的？

**推荐回答：**在同一个冻结 V3 自动评分器下，对低输出预算和高输出预算的两批响应重新统计，低预算 461/605，高预算 572/605，净增 111。输出上限由 2048 提高到 16384，截断响应从 117 降到 6，总 token 从 687,195 增到 1,068,216，增加 55.45%。这是预算和完成率对照，不是等预算推理增益，也不是算子路由结果。[S7]

### Q94｜P0：328、407、461、572、597 为什么这么多分数？

**回答要点：**必须同时说输出来源和评分口径：

| 输出来源 | 原提取/比较 | 完整 V3 自动评分 | 事后复核 |
|---|---:|---:|---:|
| 低预算 2048 | 328/605 | 461/605 | 不把它补写成同等级全量人工认证 |
| 高预算 16384 | 407/605 | 572/605 | 597/605，含 25 个事后修正 |

**关键边界：**597 不是自动评分成绩；报告说明是 Codex 对 33 个未通过响应的事后数学核查，并非独立人类专家逐条认证全部 605 题。[S7]

### Q95｜P0：提分是不是只是把评分器改宽松了？

**推荐回答：**要把同一响应重评与不同响应生成分开。低预算同一批输出从 328 到 461，反映提取和数学判定改变；统一 V3 后不同预算输出从 461 到 572，减少了评分器变化这个混杂，但仍有采样和预算差异。评分器不能为了通过而宽松接受，应保留 Unknown、限制近似判等，并独立审计假阳性和假阴性。[S7]

### Q96｜P0：怎么证明 111 题主要来自截断改善？

**回答要点：**逐题对齐显示，统一 V3 下新增 111 题中，105 道原先截断、4 道原为 Unknown、2 道原为 incorrect；原来 117 道截断中有 6 道高预算后仍截断。这个证据很符合完成率解释，但两批响应是独立采样，不能断言每一道变化都由预算单独造成。[S7]

### Q97｜P1：max_tokens=16384 是每题都输出 16384 吗？

**回答要点：**不是，它是单次调用输出允许上限，实际使用由响应 usage 决定。reasoning token 也可能占输出预算，所以输出可见文本短不代表没有耗尽预算。比较要记录结束原因、完整响应和实际 token，而不是只看上限。

### Q98｜P0：最终答案提取器改了什么？

**回答要点：**从首个 boxed、简单截断等策略改为平衡花括号解析，结合显式最终提交选择和完整性判断，避免嵌套分数被切断或早期候选被误当终答。不能利用标准答案选择哪个候选，也不应从隐藏 reasoning 中补写未提交终答。多个冲突候选应保守处理。[S7]

### Q99｜P0：类型化数学等价判定具体是什么？

**回答要点：**先确定题目要求的答案类型，再提取与规范化，最后进行相应比较。数值、表达式、集合、区间、向量、矩阵和单位语义不同，不能统一字符串比较；集合可能无序，向量一般有序，开闭区间不能混淆。解析与规格不明确时返回 Unknown。[S7]

### Q100｜P1：为什么不能只用浮点误差或 SymPy simplify？

**回答要点：**浮点近似相等不保证表达式全域等价；符号化简也可能忽略定义域、分支、单位或题目要求的全部解。应采用精确有理数、受限符号运算和类型约束，数值抽查只能辅助发现反例。符号比较也要有超时和表达式复杂度限制。

### Q101｜P1：正确、错误、Unknown、不完整怎么区分？

**回答要点：**正确表示当前协议下可确认等价；错误表示可确认不满足；Unknown 表示无法可靠确定；不完整表示未形成有效最终提交。主成功率中后三类都不算通过，但失败归因要分别统计，避免把所有未通过都说成模型不会解。

### Q102｜P1：参考答案会不会反向影响提取？

**回答要点：**预测提取只应依赖题目公开规格与预测响应，不能根据 gold 在多个候选里挑一个。比较阶段可以使用参考，但要保留提取与比较的接口隔离和日志；如果同一模型同时判题面、参考和预测，尤其要防止隐式泄漏。

### Q103｜P0：代码选块为什么需要入口函数感知？

**回答要点：**响应可能同时含解释性代码、错误草稿和最终实现，取第一个代码块可能执行错对象。根据公开任务签名或公开测试的入口函数，优先选择语法完整且包含入口的代码块，按固定规则回退；不能运行隐藏测试后挑最高分代码块，也不能根据 gold 选块。[S7]

### Q104｜P0：MBPP 94.40%→96.80% 是 pass@1 吗？

**推荐回答：**不是标准盲测 pass@1。它是 500 题在 FlowEvo 原生测试反馈恢复、最多多候选及在线成功库流程中的最终通过率，472→484，增加 12 题、2.40 个百分点。预算与提取同时变化，也存在题序和在线库状态影响，所以不能说纯靠提取改进了 2.4 个百分点。[S7]

### Q105｜P1：五个基准都提升了吗？

**回答要点：**没有。历史对照中 MATH、MBPP、GSM8K 自动通过数上升；HumanEval 163/164 持平；ALFWorld 129/134→128/134，下降 1。不同任务的评分和恢复机制不同，不能合并成一个“平均提升”来掩盖负结果。[S7]

### Q106｜P0：token 怎么统计，为什么要 API 账本？

**回答要点：**总 token 为输入加输出，reasoning 是输出子集，不能重复加。失败、截断、原生重试和相关建库请求也计入。runner 可能因空终答提前报错而漏记用量，所以以逐请求原始 API 账本对齐。未知 usage 单列或给明确假设下上界，不能当作零成本。[S7]

## 第十部分：工程实现与现场设计（Q107—Q118）

### Q107｜P0：请画系统架构并说明数据流。

**回答要点：**把离线构建与在线执行画开，隐藏数据不回流到候选修复。最重要的是标明数据权限、版本、失败分支和成本账本，而不是堆模块名称。

```text
离线：开发题与运行轨迹
        ↓ 审计与稳定失败筛查
      机制假设 → 结构化规格 → 候选生成
                               ↓ 静态/开发/边界验证
                            冻结候选
                               ↓ 独立隐藏确认与回归
                         算子库 + 版本证据

在线：题目 → 特征/边界检查 → 证据路由 → 专项执行 → 最终响应
                              ↓ 不满足      ↓ 拒绝/异常
                            通用回退 ←───────┘

旁路：原始请求响应、调用ID、用量、路由决策、评分版本、错误原因
```

### Q108｜P1：算子库怎么存储，为什么先用 JSON？

**回答要点：**当前库用 JSON 保存记录，并有追加式证据审计日志，适合小规模研究、可读与版本追踪。生产并发下需事务存储、唯一键、不可变 artifact 和证据快照；不要把当前文件存储说成已经解决了多机一致性。[S3]

### Q109｜P1：并发评测如何避免数据串扰？

**回答要点：**独立模型会话和结果对象，用信号量控制并发；按问题、重复编号、方法、请求 ID 关联日志。在线库需要固定快照或明确允许更新，随机交错可以减少时段偏差。后者是实验设计要求，是否历史已做到要看运行协议，不能一概而论。

### Q110｜P1：如何断点续跑、避免重复计费？

**设计回答：**给任务与物理请求生成稳定 ID，持久化请求状态、结果和 usage，写入采用原子替换或事务。重启优先复用已完成 checkpoint，超时未知请求不要自动当作没发出。逻辑任务和物理调用分开计数，重复响应去重，重试仍计成本。

### Q111｜P1：API 失败如何处理？

**回答要点：**区分限流、连接失败、服务端错误、模型拒绝、空响应与截断。重试策略必须提前冻结，并把所有物理调用计入账本。正式评测不要在不知道原请求是否计费的情况下无限重试，也不要把 API 故障归为数学错答。

### Q112｜P0：asyncio.wait_for 能中断 CPU 死循环吗？

**推荐回答：**不能保证。它主要依靠协程可取消点；若同步 CPU 计算阻塞事件循环，定时器和取消可能不能及时生效。CPU 工具应放到可终止的独立 worker，并设置进程级 CPU、内存、墙钟限制。线程超时也不等于终止底层线程。历史外层 180 秒是协议上限，不应包装成任意同步代码的强隔离保证。

### Q113｜P1：哈希校验通过就能安全动态加载吗？

**回答要点：**哈希只说明加载内容匹配被冻结版本；如果被冻结代码本身恶意或有漏洞，仍不安全。还要限制 artifact 来源、导入副作用与权限，把验证和加载置于隔离环境。类源码哈希也要结合依赖与执行环境，防止相同包装调用了不同实现。

### Q114｜P1：怎么写测试？哪些最重要？

**回答要点：**核心算法用小规模独立 oracle 和性质测试；路由测正例、近似反例、冲突与拒绝；版本测源码变更后证据失效；集成测失败回退、共享预算和日志关联；评分器测假阳性与假阴性。不要只写“调用函数得到自己预先算出的同一个结果”的实现镜像测试。

### Q115｜P1：遇到算子结果与 LLM 自检冲突，信谁？

**设计回答：**根据验证器可靠性和可证明条件决策，而不是默认相信更自信的文本。对确定性算法先核对参数解析与域内条件；独立验证无法决断时保留不确定或回退。若引入二次检查，应计入共同预算，并评测检查器错误覆盖正确工具结果的风险。

### Q116｜P1：失败日志里有提示注入怎么办？

**回答要点：**题目、轨迹和工具输出都作为不可信数据，不给它们系统权限。机制归纳通过固定 schema 和片段引用处理，工具权限不能由日志中的指令改变；生成代码仍走验证。文本隔离提示只能降低风险，真正的权限控制要由运行环境执行。

### Q117｜P2：上线后需要监控哪些指标？

**设计回答：**全请求成功率、专项覆盖率、误触发、拒绝率、回退原因、超时、P50/P95 时延、模型与工具成本、各版本表现，以及 Unknown 和输入漂移。分别监控“路由选择了谁”和“最终执行了谁”，避免回退把错误调用掩盖掉。

### Q118｜P1：现场让你写路由主流程，怎么写？

**设计回答：**先写共享预算和可观测性，再写选择与回退。下面是设计伪代码，不代表当前实现已具备全部进程级强限制。

```python
def solve(problem, budget, snapshot):
    context = extract_public_features(problem)
    candidates = retrieve(snapshot, context)
    eligible = [c for c in candidates
                if not hard_blocked(c, context)
                and evidence_valid_for_revision(c)
                and evidence_gates_pass(c)]
    selected = choose_or_decline(eligible)
    if selected is not None:
        result = run_in_killable_worker(selected, problem, budget.remaining())
        log_attempt(selected, result, budget)
        if result.status == "success" and output_contract_valid(result):
            return result  # 接口合法不等于语义必然正确
    return generic_fallback(problem, budget.remaining())
```

## 第十一部分：业务落地与方案比较（Q119—Q128）

### Q119｜P1：这种方法适合什么业务？

**回答要点：**重复出现、输入结构可抽取、目标可验证且精确计算容易出错的任务，例如受约束计数、规则校验、数据转换和代码检查。对开放式创作、没有可靠反馈或高频变化的任务，算子准入和收益评估更难。应用场景是设计迁移，不代表已上线这些业务。

### Q120｜P1：在游戏业务里怎么用？

**设计回答：**可以从配置合法性检查、活动奖励规则校验、经济系统有限约束计算或重复数据处理任务切入。先离线回放真实失败、建立确定性校验器，再以建议模式和灰度方式引入；会修改线上资产的动作需要独立权限边界。不要声称已经在网易业务部署。

### Q121｜P1：它与 RAG 的区别是什么？

**回答要点：**RAG 主要检索外部信息，算子库提供可执行能力及适用证据。两者可以结合：先检索候选说明，再检查结构化条件和版本证据。检索相似度不能直接替代“这个工具能安全正确处理该输入”的判定。

### Q122｜P1：它与微调有什么区别？

**回答要点：**微调把行为写进参数，算子把部分能力外置为可更新、可回滚、可验证的组件。算子适合精确且结构化的能力，微调可能改善通用策略与语言覆盖。要比较训练、部署、推理与维护总成本，不必把两者视为互斥。

### Q123｜P1：它与 Agent memory 或 skill learning 有什么关系？

**回答要点：**经验可以只保存文本，也可以保存程序或策略。本项目强调可执行算子的规格、验证、版本证据和选择性调用。与技能学习有交集，但“有记忆”不自动意味着可靠复用；要看能否检查适用域并控制负迁移。

### Q124｜P1：为什么不用更强模型直接解决？

**回答要点：**这是必须加入的基线。若更强模型在成本和时延约束内已能稳定解决，就不一定值得维护工具。项目价值需要在同模型控制之外，再与可用强模型和临时工具方案比较，不假定所有失败都该由新增算子解决。

### Q125｜P1：如何迁移到代码生成或软件修复？

**设计回答：**可将重复的格式处理、API 迁移、测试修复策略封装为能力，但代码反馈存在测试不充分与补丁过拟合。需要公开/隐藏测试隔离、回归、资源控制与最小权限，区分“通过当前测试”与“真实语义修复”。不能直接套用数学精确 oracle 的可信程度。

### Q126｜P1：数据漂移后路由怎么保持可靠？

**设计回答：**监控特征与拒绝分布，分版本积累真实反馈，在独立滚动验证集上校准；出现未知输入时优先拒绝而非扩大规则。漂移下重新估计覆盖与净收益，保留灰度、回滚和人工复核入口。当前小规模静态实验未验证长期漂移。

### Q127｜P1：什么时候删除一个算子？

**设计回答：**当它没有独立收益、与更好算子重复、维护成本过高、证据过期或风险不可控时。先停止新路由并保留历史 artifact 与证据，再做依赖和回归确认；不要删除审计记录。退役不是掩盖负结果，而是生命周期管理。

### Q128｜P1：如果只有一个月，你优先做什么？

**推荐回答：**先固定一个清楚的机制与同权限强基线，完善来源和全成本记录；然后构造不依赖被测工具筛选的独立测试，做单工具、双工具和路由消融；最后跑独立自然样本估计真实覆盖与净收益。优先补实验识别力，而不是只增加有利构造种子。

## 第十二部分：尖锐质疑与反思（Q129—Q136）

### Q129｜P0：“这就是你手写两个工具加 if-else，有什么研究价值？”

**推荐回答：**这个质疑指出了当前证据边界。历史两个 v2 工具有人类先验和确定性材料化，路由也偏规则化，所以我不会把它说成完全自主发现通用算法。它首先验证了“能力单元有边界、有证据、能协同且可回退”的工程闭环。要证明自动生成与选择机制的研究价值，需要独立生成轨迹、同权限临时编程基线、工具与路由消融和更多未见实例；这些应分别拿结果说明。

### Q130｜P0：“你的提升是不是专门挑了基线最不会的题？”

**推荐回答：**专项题确实围绕已诊断失败机制构造，而且有工具与路由适用性校验，因此会富集可受益样本。这有助于回答机制补足是否可行，却不能估计自然流量收益。我会保留专项/非专项分项与全部退化，并在独立自然数据、无被测工具筛选的固定样本上验证覆盖和净增。

### Q131｜P0：“同模型但多了计算工具，比较是不是不公平？”

**推荐回答：**如果问题是比较完整系统能力，允许方法多一个验证过的工具是干预本身；如果问题是证明自动生成比临时编程或普通工具更好，就必须给基线同等执行权限与预算。历史 144 观测实验不能单独回答后者，我会把它的结论限定为系统级协同收益，再用工具权限对齐的实验补足。

### Q132｜P0：“你到底证明了什么，没证明什么？”

**回答要点：**证明措辞最好改为“现有证据支持”。支持有限已知机制内的跨实例执行、双工具协同、限时成功提升与日志可审计；不支持完全无人参与、任意任务自动发明算法、自然分布必涨 25 个百分点、百工具零冲突或绝对安全。FlowEvo 线另外支持评测误判和截断对观测成绩的重要影响。

### Q133｜P1：“你做过什么失败实验，学到了什么？”

**回答方式：**可以讲主实验的非专项回归、FlowEvo 在 ALFWorld 下降或高预算成本上涨，说明自己没有只报告好结果。若讲额外研究，资料中还有反事实推理压缩小原型：4 道独立题同为 4/4，但状态控制器 token 从 2008 增到 3540，且未优于简单规则，最终 NO-GO。只有确实参与并能解释该实验时才使用，不把它说成简历主线成果。[S12]

### Q134｜P1：“如果重新做，最先改哪三点？”

**推荐回答：**第一，测试构造与被测工具解耦，减少方法相关筛选；第二，基线对齐 Python 权限、调用与工具预算，并完整计入离线成本；第三，预先固定主比较与统计单位，保存所有候选、正式失败和模型请求版本。这样比继续堆成功案例更能回答可信性问题。

### Q135｜P1：“如何让别人复现？”

**回答要点：**提供代码与依赖快照、模型配置和实际响应标识、数据生成规则与种子、数据/算子/评分器哈希、全量原始响应与请求账本、候选修复轨迹、冻结协议和统计脚本。没有不可变服务权重时，应区分离线结果重算可复现与线上重新生成只能统计复现。

### Q136｜P0：“用一句话概括你最大的收获。”

**推荐回答：**Agent 的可靠提升不能只看最终分数，必须先确认失败是什么，再把新增能力的适用边界、独立验证、运行成本和退化都记录清楚。

## 面试前必须准备的三个案例

### 案例 A：括号化去重的完整闭环

按此顺序讲：模型将括号化方案数与不同结果数混淆 → 提取目标“保序、固定运算符、结果去重” → 形成区间集合 DP → 验证小规模暴力枚举和近似反例 → 冻结参数域与版本 → 路由识别不同结果计数 → 超域或解析失败回退。能现场写出状态转移，并说明复杂度不是单纯 O(n³)。

**必须区分：**算法推导示例不代表你已经在当年所有版本中运行了同样的差分测试；未保存证据的检查只能说“应该做”或“可以这样验证”。

### 案例 B：非专项回归

主种子非专项 87/96→84/96；两道题导致三次退化，均进入通用回退。说明“没有误路由”与“系统没有退化”不同，原有工作流重新采样与超时仍可能造成损失。不要用解释性归因删除主指标中的负样本。

### 案例 C：评分与生成变化分开

拿同一批低预算输出：原判定 328、V3 判定 461，说明评测覆盖变化；再在冻结 V3 下比较低高预算 461→572，说明更高预算与完成率变化。最后指出不同预算输出不是同一随机样本，且费用增加 55.45%。不把 597 事后复核当自动成绩。

## 三段可直接练习的口述稿

### 30 秒版

我做的是失败驱动的 Agent 能力沉淀：从可复现失败归纳需求，生成并验证可复用算子，再根据输入边界和版本证据选择性调用，不适用就回退。一个双算子构造混合集里，48 道题各跑 3 次，限时正确数从 96/144 到 132/144。我也做了提取、评分和 API 用量审计，区分真正能力缺口与截断、评测问题。当前是有人工参与的闭环，结果主要支持有限机制内复用。

### 90 秒版

这个项目关注固定工具库覆盖不到的长尾失败。我先把模型错答、执行故障、截断和评分误判分开，再对同题重复和跨题一致性做筛查，形成明确输入输出与适用边界的需求规格。候选必须通过静态检查、受限执行、边界反例、隐藏确认和回归，代码版本与证据绑定，不能生成出来就上线。

在线路由使用可观察输入特征、硬失败边界和历史配对证据，不调用 LLM；没有安全匹配就回退通用两阶段流程。两个案例分别是括号化去重的区间 DP 和受限数字素数枚举。48 道构造题各跑 3 次，严格正确从 96 到 132，专项 48 次观测全部成功，超时从 39 到 1，但非专项也有 3 次退化。

这个实验有明确边界：工具和协议先冻结，但数据构造做过工具与特征适用性校验，因此是协同可行性证据，不能直接当自然分布收益。另一个 FlowEvo 对照里，我统一评分器后观察到更高输出预算减少截断，同时完整报告 token 上涨，避免把预算或评测收益误归因给算子机制。

### 遇到实验可信性质疑时的 60 秒版

144 是 48 道题各重复 3 次，不是 144 道独立题。里面有 16 道专项、24 道普通题和 8 道近似反例，工具版本与准备协议在生成数据前冻结，正式运行前再绑定数据、路由和评分器哈希。两组同模型配置、同 180 秒总上限，但我不会把它说成等全部计算成本。

归因证据是专项增加 39 个正确、非专项减少 3 个，所以净增 36，且专项调用轨迹与预期一致。不过构造时做过工具与路由适用性校验，当前结论是有限范围的算子加路由协同，而不是无偏自然泛化。要独立证明路由贡献和自动生成贡献，需要固定工具的路由消融、同权限临时编程基线与独立自然样本。

## 可选补充：如果被问“有没有更严格的自动生成与同权限预算实验？”

可以介绍后续 Experiment A，但必须先说明它**不是简历 144 条实验的协议**，也不是自动路由实验。[S10]

- 生成器只获公共规格、30 道独立小规模训练样例及答案、环境及自己候选的验证反馈；报告记载选中 candidate 3，repair 0，没有人工改源码或复制参考实现。
